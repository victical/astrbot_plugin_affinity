# astrbot_plugin_affinity 好感度与关系系统设计文档

## 1. 文档目的

本文档定义新增 `astrbot_plugin_affinity` 独立插件，并将 `astrbot_plugin_engram` 中现有“羁绊系统”迁移为“好感度与关系系统”的设计方案，覆盖：

- 记忆插件与好感度插件的拆分边界
- 好感度数据模型与存储方式
- 正负向事件与每日回顾结算
- 关系档位、确认关系与锁档规则
- 群聊/私聊的全局表现方式
- LLM 说话风格注入
- 旧羁绊数据迁移方案
- 记忆插件只读接口契约
- 数据库幂等与状态派生规则
- 关系确认状态机与配置边界

本文档仅描述设计，不包含实现代码。

---

## 2. 设计背景

当前项目中的“羁绊系统”存在以下体验问题：

1. 升级门槛偏硬，多个条件同时满足时才会升档。
2. 数值增长不够直观，用户难以感知关系变化。
3. 没有足够鲜明的“关系推进”体验。
4. 负面互动、吃醋、冷战等剧情感不足。

因此，本次改造将羁绊系统升级为更具情绪与关系感知的“好感度与关系系统”。

---

## 3. 设计目标

1. 使用单轴好感度表达关系进展，范围为 `-100 ~ 520`。
2. 好感度是全局状态，同一 `user_id` 在私聊与群聊中共享。
3. 好感度与记忆系统拆分为独立插件，但好感度插件强依赖记忆插件。
4. 关系档位覆盖友情线与恋爱线，支持确认关系。
5. 恋人确认后锁档，不再掉回低档位。
6. 每个阶段有独立说话风格。
7. 好感增长既受实时互动影响，也受每日回顾影响。
8. 不做会话隔离，同一 `user_id` 全局共用一份好感与关系状态。
9. 借鉴 FavourPro 的多维内心状态、状态驱动话术与管理命令思路，但避免字段化输出污染最终回复。

---

## 4. 插件拆分方案

## 4.1 记忆插件

 `astrbot_plugin_engram`，负责：

- 原始消息记录
- 长期记忆归档与检索
- 用户画像
- 聊天统计
- 每日总结与画像提取
- 对外提供只读接口

该插件是事实源，不承载关系状态。

## 4.2 好感度插件

建议新增 `astrbot_plugin_affinity`，负责：

- 好感度数值
- 正负事件记录
- 关系档位
- 确认关系
- 锁档规则
- 每日回顾结算
- LLM 关系风格注入

该插件强依赖记忆插件，启动时必须能读取记忆插件暴露的接口。

## 4.3 依赖规则

- 好感度插件不能直接读写记忆插件内部 SQLite / JSON 文件。
- 好感度插件只通过公开接口获取画像、统计、总结结果。
- 记忆插件不反向依赖好感度插件，避免循环耦合。
- 若记忆插件不可用，好感度插件直接禁用，不进入降级模式。
- 好感度状态不按群、私聊或会话切分，统一按 `user_id` 全局保存。

---

## 4.4 FavourPro 借鉴边界

本设计参考 `astrbot_plugin_favourpro` 的以下方向：

- 多维内心状态：把关系体验拆成数值、印象、关系阶段等多个内部维度。
- 状态驱动话术：不同状态影响回复风格，而不是只显示一个分数。
- 自动注入：在 LLM 请求前注入关系风格提示，让关系自然流露。
- 管理命令：提供查询、设置、重置等维护入口。
- 独立存储：好感系统有自己的数据目录和状态记录。

但本设计不照搬以下做法：

- 不做会话隔离，不提供 `session_based` 式按群/私聊切分。
- 不把内部状态以 `好感度:`、`关系:`、`印象:` 等字段模板直接喂给最终回复模型。
- 不让模型同时承担事件判断、分数结算、状态存储和用户回复。
- 不把结构化状态直接作为用户可见消息输出。

核心原则：

- 内部状态可以结构化。
- LLM 注入必须自然语言化。
- 用户可见回复必须保持自然对话，不暴露内部字段。
- 分数变化必须通过事件日志追溯，而不是靠模型自由发挥。

## 4.5 记忆插件只读接口契约

好感度插件依赖记忆插件，但依赖边界必须收敛到一个稳定的只读 Provider。推荐由 `astrbot_plugin_engram` 暴露 `AffinityMemoryProvider`，好感度插件启动时通过 AstrBot 插件上下文或服务注册表获取该 Provider。

### 必需接口

| 方法 | 用途 | 返回要求 |
|---|---|---|
| `get_user_profile(user_id)` | 读取当前用户画像 | 返回 dict；不存在时返回空画像，不抛内部存储异常 |
| `get_profile_delta(user_id, date)` | 读取指定日期画像新增/变化 | 返回新增偏好、禁忌、称呼、关系信息等摘要 |
| `get_interaction_stats(user_id, date)` | 读取指定日期互动统计 | 返回有效消息数、有效轮次、首次/末次互动时间、累计聊天天数 |
| `get_daily_summary(user_id, date)` | 读取指定日期每日总结 | 返回自然语言摘要和结构化标签 |
| `get_memory_refs(user_id, date, limit)` | 读取指定日期形成或命中的长期记忆引用 | 返回记忆 ID、摘要、来源时间，不返回完整私密原文 |
| `get_memory_count(user_id)` | 迁移与初始评分使用 | 返回当前长期记忆数量 |
| `get_legacy_bond_snapshot(user_id)` | 旧羁绊迁移使用 | 返回旧等级、旧进度、旧分数明细；没有旧数据时返回 `None` |

### 可选接口

| 方法 | 用途 |
|---|---|
| `register_daily_review_listener(callback)` | 记忆插件完成每日总结后通知好感插件 |
| `get_all_known_user_ids()` | 批量迁移和补跑每日回顾 |

### 契约约束

- Provider 只返回业务结果，不暴露 SQLite 路径、JSON 路径、Chroma collection 等内部对象。
- 好感插件不得持有 `MemoryManager`、`ProfileManager`、`DatabaseManager` 的内部实例。
- Provider 返回数据必须可序列化，方便后续测试、缓存和回放。
- Provider 异常必须归一化为“记忆系统不可用 / 用户数据不存在 / 当日数据未生成”三类错误。
- 若必需接口缺失，`astrbot_plugin_affinity` 启动失败并输出明确日志；若仅可选接口缺失，则使用定时兜底。

## 5. 数据模型

## 5.1 好感度主表

每个用户一条全局状态：

- `user_id`
- `affinity_score`：`-100.0 ~ 520.0`
- `stage`：按分数计算出的基础阶段快照
- `effective_stage`：运行时实际生效阶段，通常由 `stage` 与 `lover_locked` 派生
- `confirmed_stage`：已确认关系阶段
- `custom_nickname`：专属称呼
- `lover_locked`：恋人确认后锁档
- `impression_tags_json`：隐藏印象标签
- `current_mood`：短期情绪
- `last_interaction_at`
- `last_negative_at`
- `last_proactive_prompt_at`
- `daily_review_at`
- `created_at`
- `updated_at`

说明：该表按 `user_id` 全局唯一，不存在 `session_id` 维度，不做会话隔离。

内部状态可扩展为多个隐藏维度：

- `affinity_score`：单轴好感度，决定整体阶段。
- `impression_tags`：印象标签，如可靠、温柔、疏离、敏感等。
- `relationship_stage`：关系阶段，如初识、朋友、挚友、暧昧、恋人候选、恋人。
- `current_mood`：短期情绪，如平静、开心、吃醋、低落、冷战。

这些维度仅用于计算和注入风格，不直接展示到普通回复中。

推荐表名为 `affinity_user_state`，`user_id` 为主键。`stage` 和 `effective_stage` 可以持久化为便于查询的快照，但每次分数或锁档状态变化后都必须重新计算，不能由 LLM 直接写入。

## 5.2 事件表

用于解释好感变化来源：

- `id`
- `user_id`
- `event_type`
- `score_delta`
- `reason`
- `source`
- `source_ref`
- `message_id`
- `event_date`
- `idempotency_key`
- `metadata_json`
- `created_at`

建议支持的事件类型：

- `daily_chat`
- `memory_recall`
- `profile_growth`
- `daily_review`
- `share_secret`
- `shared_worry`
- `jealousy`
- `rejection`
- `cold_war`
- `argument`
- `relationship_confirm_requested`
- `relationship_confirmed`

推荐表名为 `affinity_events`。事件表是审计来源，任何分数变化都必须先生成事件，再由规则引擎应用到主表。

### 幂等规则

- 每个会改变分数的事件必须写入 `idempotency_key`。
- 实时消息事件建议使用 `message:{message_id}:{event_type}`。
- 每日回顾事件建议使用 `daily:{user_id}:{event_date}:{event_type}`。
- 迁移事件建议使用 `migration:{user_id}:{migration_version}`。
- `idempotency_key` 必须有唯一约束；重复写入时跳过，不再次加扣分。
- 对于没有 `message_id` 的自然语言触发事件，必须使用时间窗口和业务上下文生成稳定键，例如 `confirm:{user_id}:{event_date}`。

## 5.3 状态表

用于控制推进和冷却：

- `user_id`
- `proactive_cooldown_until`
- `confirmation_status`：`none` / `pending` / `confirmed` / `rejected`
- `confirmation_initiator`：`user` / `bot` / `admin`
- `confirmation_started_at`
- `confirmation_expires_at`
- `last_confirmation_attempt_at`
- `last_rejected_at`
- `stage_locked`
- `cooldown_reason`
- `updated_at`

推荐表名为 `affinity_runtime_state`。该表保存流程状态，不直接表达关系事实；关系事实仍以 `affinity_user_state.confirmed_stage` 和 `lover_locked` 为准。

## 5.4 每日计数表

为了执行日上限和幂等补跑，建议增加 `affinity_daily_counters`：

- `user_id`
- `event_date`
- `realtime_positive_delta`
- `review_positive_delta`
- `negative_delta`
- `daily_chat_turns`
- `profile_growth_count`
- `memory_recall_count`
- `counters_json`
- `updated_at`

唯一键为 `user_id + event_date`。该表只用于限制当天累计变化，不作为最终审计来源；最终解释仍读取 `affinity_events`。

## 5.5 存储位置

好感插件使用自己的数据目录和 SQLite 文件：

- SQLite：`affinity.db`
- 日志与调试导出：`affinity_logs/`
- 迁移备份：`affinity_migration_backups/`

不得复用或写入 `engram_memories.db`、`engram_personas/` 或 ChromaDB 目录。

## 6. 好感度范围与阶段

## 6.1 单轴范围

好感度使用单轴：

- 最低：`-100`
- 最高：`520`

## 6.2 负向阶段

| 区间 | 阶段 | 含义 |
|---|---|---|
| `-100 ~ -71` | 冷战 | 明显排斥，互动降温 |
| `-70 ~ -31` | 反感 | 厌烦、争吵、要求保持距离 |
| `-30 ~ -1` | 疏离 | 轻度不满、谨慎回应 |

## 6.3 正向阶段

| 区间 | 阶段 | 含义 |
|---|---|---|
| `0 ~ 49` | 初识 | 默认普通状态 |
| `50 ~ 149` | 朋友 | 基础熟悉 |
| `150 ~ 299` | 挚友 | 稳定亲近 |
| `300 ~ 439` | 暧昧 | 可出现试探、吃醋、拉扯 |
| `440 ~ 519` | 恋人候选 | 可低频推进确认关系 |
| `520` | 恋人 | 满好感，确认后锁档 |

说明：

- `520` 不是自动恋人。
- 只有在用户确认后，才写入 `confirmed_stage = 恋人`。
- 未确认前，即使到 `520` 也只是恋人候选。

## 6.4 阶段派生规则

系统内部区分三个概念：

- `score_stage`：只由 `affinity_score` 区间计算得出。
- `confirmed_stage`：用户明确确认后的关系事实。
- `effective_stage`：实际用于命令展示、主动推进和 LLM 注入的阶段。

派生规则如下：

1. 每次分数变化后，先把 `affinity_score` clamp 到 `-100 ~ 520`。
2. 根据分数区间计算 `score_stage`，并写入主表 `stage`。
3. 若 `lover_locked = true` 且 `confirmed_stage = 恋人`，则 `effective_stage = 恋人`。
4. 若未锁档，则 `effective_stage = score_stage`。
5. 即使 `effective_stage = 恋人`，`current_mood` 仍可被负面事件更新为低落、吃醋、冷战等短期情绪。
6. 恋人锁档后，负向事件仍然可以扣分和记录，但不得把 `effective_stage` 降为暧昧、挚友、朋友或更低。

管理命令展示时应同时展示 `affinity_score`、`stage`、`effective_stage`、`confirmed_stage` 与 `lover_locked`，避免管理员误以为锁档后分数不再变化。

## 7. 正负事件规则

## 7.1 正向加分

建议采用“实时小加分 + 每日回顾大结算”的双层策略。

### 实时互动

| 事件 | 建议分值 |
|---|---:|
| 每天首次有效互动 | `+6` |
| 当天持续有效聊天 | `+0.8/轮`，日上限 `+8` |
| 主动分享喜好 / 画像信息 | `+4/项`，日上限 `+12` |
| 分享心事 / 烦恼 / 秘密 | `+10 ~ +20` |
| 成功调用并引用相关记忆 | `+0.5 ~ +1.5` |
| 用户正向回应“你还记得” | `+3 ~ +8` |

### 每日回顾

| 事件 | 建议分值 |
|---|---:|
| 当天有有效陪伴 | `+4 ~ +6` |
| 形成长期记忆 | `+0.5/条`，日上限 `+5` |
| 新增明确画像信息 | `+4/项`，日上限 `+12` |
| 提到共同经历 / 长期陪伴 | `+3 ~ +8` |
| LLM 判定当天关系升温 | `+2 ~ +8` |

## 7.2 负向扣分

| 事件 | 建议分值 |
|---|---:|
| 轻微冷淡 / 拒绝推进 | `-2 ~ -5` |
| 短暂争执 / 不满 | `-5 ~ -12` |
| 严重争吵 / 明确厌烦 | `-15 ~ -35` |
| 要求保持距离 / 强烈排斥 | `-30 ~ -60` |
| 冷战持续 | 每日 `-3 ~ -8` |

说明：

- 吃醋只在暧昧或恋人阶段作为剧情波动，不归入反感档的主要来源。
- 玩笑、角色扮演、撒娇式抱怨不直接扣分。
- 所有加扣分都应有日上限，避免刷分或一次性打崩关系。

## 7.3 日上限与防刷规则

建议默认上限：

| 类型 | 默认上限 |
|---|---:|
| 实时正向总加分 | `+20/日` |
| 每日回顾正向总加分 | `+25/日` |
| 单日正向总加分 | `+35/日` |
| 单日负向总扣分 | `-60/日` |
| 记忆命中加分 | `+5/日` |
| 画像新增加分 | `+12/日` |

防刷规则：

- 同一用户同一天首次有效互动只结算一次。
- 连续短消息合并为有效轮次后再加分，避免刷屏。
- 同一条记忆被多次命中时，当天只按首次命中加分。
- 画像新增必须来自记忆插件确认后的画像变化，不能由用户一句话直接无限加分。
- 负向事件不应被日上限完全抵消；严重排斥类事件可以突破普通扣分上限，但必须写入高风险事件日志。

## 7.4 规则引擎边界

LLM 可以输出关系趋势和候选事件，但最终分值由规则引擎计算。推荐流程：

1. 把实时消息、记忆命中、画像变化、每日总结转换为候选事件。
2. 规则引擎校验事件类型、冷却、日上限和幂等键。
3. 规则引擎计算 `score_delta`。
4. 写入 `affinity_events`。
5. 聚合事件更新 `affinity_user_state` 和 `affinity_daily_counters`。

LLM 输出不得直接包含最终分数；如果 LLM 输出无法解析，则本轮只记录调试日志，不改变好感度。

## 8. 关系确认与锁档

## 8.1 触发方式

确认关系可以由用户主动触发，也可以由 Bot 在满足条件时主动发起。

用户通过自然语言触发确认关系，例如：

- “我们是什么关系”
- “可以做恋人吗”
- “我想和你确认关系”

Bot 主动发起确认关系，例如：

- “我有点想认真确认一下，我们现在算是什么关系？”
- “如果你愿意的话，我想把我们的关系说清楚一点。”
- “我其实有点在意你怎么看我们之间的关系。”

好感插件根据当前状态、分数、冷却和场景配置判断是否进入确认流程。Bot 主动发起时只能创建 `pending` 确认状态，最终确认必须等待用户明确同意。

## 8.2 确认条件

只有在达到恋人候选区间时才允许确认：

- `affinity_score >= 440`
- `effective_stage` 不是冷战 / 反感 / 疏离
- 不处于主动推进冷却期
- `confirmation_status` 不是 `confirmed`
- 最近一次拒绝已过冷却期

若由 Bot 主动发起，还必须满足：

- 通过主动推进判定。
- 当前场景允许主动确认关系。
- 最近存在正向互动或每日回顾判定关系升温。
- 不在用户刚表达压力、回避、冷淡或负面情绪之后。

## 8.3 确认状态机

确认关系不应由单次 LLM 回复直接完成，必须通过状态机控制。

| 当前状态 | 触发 | 下一个状态 | 动作 |
|---|---|---|---|
| `none` | 用户询问关系且满足确认条件 | `pending` | 写入 `confirmation_started_at`、`confirmation_expires_at`、`confirmation_initiator = user` |
| `none` | 用户询问关系但不满足条件 | `none` | 自然回复，不写确认状态，可写轻微事件 |
| `none` | Bot 主动确认且满足确认条件 | `pending` | 写入 `confirmation_started_at`、`confirmation_expires_at`、`confirmation_initiator = bot` |
| `none` | Bot 主动确认但不满足条件 | `none` | 不发起确认，不输出确认句 |
| `pending` | 用户明确同意 | `confirmed` | 写入 `confirmed_stage = 恋人`、`lover_locked = true`、关系确认事件 |
| `pending` | 用户明确拒绝或回避 | `rejected` | 写入拒绝事件与更长冷却 |
| `pending` | 超过过期时间 | `none` | 清理 pending，不扣分 |
| `rejected` | 冷却结束 | `none` | 允许后续重新触发 |
| `confirmed` | 任意普通互动 | `confirmed` | 保持锁档 |

默认参数：

- `pending` 过期时间：24 小时。
- 用户拒绝后的主动推进冷却：7 天。
- 主动推进询问默认冷却：3 天。
- 用户主动提出确认关系不受 3 天主动推进冷却限制，但仍受拒绝冷却限制。
- Bot 主动发起确认默认只允许私聊；群聊默认关闭，除非显式开启 `affinity_group_allow_proactive_confirm`。

确认关系的用户可见回复必须自然表达，不输出“状态机”“pending”“confirmed”等内部词。

## 8.4 锁档规则

- 用户确认后，写入 `confirmed_stage = 恋人`
- `lover_locked = true`
- 关系档位不再回退到暧昧 / 挚友 / 朋友
- 分数仍可波动，但只影响情绪表达，不影响已确认关系

## 8.5 不做解除流程

本设计不包含分手、解除关系或手动解除锁档流程。

## 8.6 管理命令

参考 FavourPro 的维护入口，但保持最小必要集：

- `/好感查询 [user_id]`：查询当前好感、阶段、确认状态。
- `/好感设置 <user_id> <score>`：管理员手动修正分数。
- `/关系设置 <user_id> <stage>`：管理员手动修正关系阶段。
- `/好感重置 <user_id>`：重置用户关系状态。
- `/好感事件 <user_id>`：查看最近好感事件日志。
- `/好感回顾 <user_id> [date]`：管理员手动补跑指定日期每日回顾。
- `/好感迁移 [user_id]`：管理员手动执行旧羁绊数据迁移；不传 `user_id` 时批量迁移。

管理命令输出可以包含字段；普通聊天回复不得包含内部字段。

## 9. 主动推进规则

## 9.1 阶段驱动

| 阶段 | 推进方式 |
|---|---|
| `300 ~ 439` | 含蓄提示 |
| `440 ~ 519` | 可低频直接询问 |
| `520` | 可更明确推进确认 |

## 9.2 冷却

- 主动推进默认冷却为 **3 天一次**
- 用户拒绝或回避后进入更长冷却
- 负面阶段禁止主动推进

## 9.3 主动推进判定

主动推进分为两层：

- 普通关系推进：只决定“是否允许在回复里轻微推进关系”，不直接修改关系状态。
- 主动确认关系：在满足确认条件、冷却和场景配置时，可由 Bot 主动发起确认，并进入 `pending` 状态。

推荐判定顺序：

1. 读取 `effective_stage`、`current_mood` 和 `confirmation_status`。
2. 若处于冷战 / 反感 / 疏离，禁止推进。
3. 若 `confirmation_status = pending`，只允许围绕当前确认流程自然回应。
4. 若处于拒绝冷却期，禁止推进。
5. 若未达到本阶段分数阈值，禁止推进。
6. 若 `effective_stage` 为暧昧，可生成含蓄推进提示，不创建确认状态。
7. 若 `effective_stage` 为恋人候选或分数达到 `520`，且场景允许主动确认关系，可进入确认状态机创建 `pending`。
8. 若只通过普通冷却检查但不满足主动确认条件，只生成自然语言风格提示。

主动推进文案必须低频、可回避、不过度施压。用户回避时应进入冷却，而不是连续追问。Bot 主动确认关系时必须把问题留给用户决定，不得替用户确认关系。

## 10. 每日回顾流程

## 10.1 自动触发

记忆插件完成每日总结与画像提取后，通知好感插件执行 `daily_review`。

## 10.2 兜底触发

若联动失败，则由固定时间任务兜底执行，建议凌晨执行。

## 10.3 手动补跑

提供手动命令用于调试和补结算。

## 10.4 结算方式

建议流程：

1. 读取当天新增记忆
2. 读取当天画像变化
3. 读取当天互动统计
4. 调用 LLM 输出关系事件分析
5. 规则引擎计算分数
6. 写入事件日志
7. 更新阶段与冷却状态

LLM 只负责判断趋势与事件，不直接决定最终分值。

## 10.5 幂等与补跑

每日回顾必须支持重复执行，重复执行不得重复加分。

规则：

- 每日回顾以 `user_id + event_date` 为结算粒度。
- 每个每日事件写入 `idempotency_key = daily:{user_id}:{event_date}:{event_type}`。
- 若同一天已完成回顾，普通自动任务直接跳过。
- 管理员手动补跑时可以选择 `dry_run` 或 `force_rebuild`。
- `dry_run` 只输出候选事件和预计分值，不写库。
- `force_rebuild` 必须先撤销当天由每日回顾产生的事件影响，再重算并写入新事件。
- `force_rebuild` 前必须备份当天相关事件与主表状态。

每日回顾完成后更新：

- `affinity_user_state.daily_review_at`
- `affinity_daily_counters.review_positive_delta`
- 当日所有 `daily_review` 相关事件

## 10.6 失败处理

- 记忆插件当日总结未生成：跳过该用户，并在下一轮兜底任务重试。
- LLM 调用失败：不改变分数，只记录失败日志。
- Provider 返回部分数据：只结算确定性规则，LLM 趋势事件跳过。
- 数据库写入失败：整次回顾事务回滚，不允许只写事件不更新主表。

## 11. LLM 说话风格

好感度是全局状态，LLM 注入时按阶段切换语气。

| 阶段 | 风格 |
|---|---|
| 冷战 | 克制、短句、明显降温 |
| 反感 | 礼貌但疏远 |
| 疏离 | 谨慎、少量关心 |
| 初识 | 友好、客气、有边界 |
| 朋友 | 轻松自然 |
| 挚友 | 熟悉、体贴、记细节 |
| 暧昧 | 更在意对方，可试探、吃醋 |
| 恋人候选 | 明显亲近，可推进确认 |
| 恋人 | 亲密、稳定、专属称呼 |

## 11.1 群聊表现

本设计采用全局一致策略：

- 私聊与群聊都按当前关系阶段完整表现
- 同一 `user_id` 在任意场景下关系状态一致
- 群聊中默认由触发者的关系状态决定风格
- 不区分群内会话或不同群聊，同一用户的好感变化和关系推进统一结算

为降低公开场景风险，建议提供配置项：

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `affinity_group_full_expression` | `true` | 群聊是否完整表现当前关系阶段 |
| `affinity_group_soften_romance` | `false` | 群聊是否弱化暧昧 / 恋人表达 |
| `affinity_group_allow_proactive_confirm` | `false` | 群聊是否允许主动推进确认关系 |
| `affinity_private_allow_proactive_confirm` | `true` | 私聊是否允许主动推进确认关系 |

默认策略保持“全局一致”，但群聊主动确认关系默认关闭。即使关系风格在群聊中生效，也应避免过度亲密、占有欲过强或让其他群成员难以接话的表达。

## 11.2 注入格式约束

为避免“消息里出现字段”，LLM 注入不得使用以下形式：

```text
好感度: 320
关系: 暧昧
印象: 温柔、可靠
```

应改为自然语言风格提示：

```text
你和当前用户已经非常熟悉，交流时可以更自然、更关心对方，但不要在回复中提到任何内部数值或字段。
当前关系有暧昧感，可以有轻微试探和在意，但不要主动越界，也不要输出“好感度”“关系阶段”等字段。
```

注入内容必须明确要求：

- 不输出内部数值。
- 不输出字段名。
- 不解释系统状态。
- 只通过语气、称呼和回应方式体现关系。

## 11.3 注入数据边界

LLM 注入层只接收 `effective_stage` 对应的自然语言风格提示、少量称呼偏好和必要的短期情绪描述。不得注入：

- 原始 `affinity_score`。
- `idempotency_key`、事件 ID、数据库字段名。
- 未经自然语言化处理的 `impression_tags_json`。
- 管理命令输出。

注入文本应由固定模板生成，模板输入来自规则引擎的枚举值，避免把 LLM 自己生成的关系分析再次喂回最终回复模型。

## 12. 与记忆系统的交互

好感插件从记忆插件读取：

- 用户画像
- 长期记忆摘要
- 聊天统计
- 当日总结
- 画像新增字段

记忆插件向好感插件提供的能力应是只读接口，不直接暴露内部存储结构。

运行时交互分为三类：

1. 实时互动：消息处理阶段读取少量画像和记忆命中结果，用于生成实时候选事件。
2. 每日回顾：调度阶段读取当日总结、画像变化和互动统计，用于批量结算。
3. 迁移初始化：管理员触发时读取旧羁绊快照和历史画像，用于生成初始分数。

好感插件不得把自身分数、关系阶段或事件日志写回记忆插件。若后续记忆插件需要使用关系状态，只能通过好感插件暴露的只读查询接口读取，避免循环写入。

## 13. 迁移方案

## 13.1 初始迁移

将旧羁绊系统折算为新好感度：

- 记忆数
- 累计聊天天数
- 画像深度
- 喜好与禁忌数量
- 已有关系状态

## 13.2 迁移策略

- 先生成初始 `affinity_score`
- 再生成初始阶段
- 再生成历史事件占位
- 恋人确认状态只从旧系统中“推断可疑似”，不直接强制锁定

## 13.3 初始分数公式

旧羁绊系统已有 100 分制的多维评分思路。迁移时推荐转换为新系统的保守初始分，不直接给到恋人确认。

推荐公式：

```text
memory_part = min(120, 120 * log(1 + memory_count / 150) / log(1 + 3000 / 150))
days_part = min(100, old_days_score / 25 * 100)
profile_part = min(100, profile_depth_pct)
preference_part = min(60, (likes_count + dislikes_count) * 6)
special_part = shared_secret ? 20 : 0
raw_score = memory_part + days_part + profile_part + preference_part + special_part
initial_affinity_score = clamp(round(raw_score), 0, 439)
```

说明：

- 迁移初始分最低为 `0`，不从历史数据生成负向阶段。
- 默认上限为 `439`，即最高迁移到“暧昧”顶部，不自动进入恋人候选。
- 若旧系统存在明确人工标记的高关系状态，可由管理员使用 `/关系设置` 或 `/好感设置` 手动调整到 `440+`。
- 不从旧数据自动写入 `confirmed_stage = 恋人`，也不自动设置 `lover_locked = true`。
- 迁移生成一条 `migration` 事件，`score_delta = initial_affinity_score`，`reason` 说明各维度贡献。

旧等级可作为保底值，避免高等级用户因单项缺失被迁移得过低：

| 旧羁绊等级 | 初始分保底 | 对应新阶段 |
|---|---:|---|
| Lv.1 | `0` | 初识 |
| Lv.2 | `50` | 朋友 |
| Lv.3 | `120` | 朋友 |
| Lv.4 | `180` | 挚友 |
| Lv.5 | `260` | 挚友 |
| Lv.6 | `340` | 暧昧 |
| Lv.7 | `420` | 暧昧 |

最终迁移分为：

```text
initial_affinity_score = min(439, max(formula_score, level_floor))
```

## 13.4 迁移幂等与回滚

- 每个用户只能自动迁移一次，幂等键为 `migration:{user_id}:v1`。
- 迁移前备份旧羁绊快照、用户画像摘要和即将写入的新状态。
- 若用户已有 `affinity_user_state`，默认跳过，不覆盖现有好感状态。
- 管理员显式 force 迁移时，必须先导出当前好感状态到 `affinity_migration_backups/`。
- 回滚只撤销迁移事件和迁移创建的初始状态，不撤销迁移之后产生的新互动事件。

## 13.5 兼容策略

旧羁绊相关展示可在迁移期保留一段时间，最终由新系统替换。

## 14. 风险与约束

1. 好感度过快上涨会破坏长期陪伴感，因此必须设置日上限。
2. LLM 误判会污染关系状态，因此最终分数必须由规则引擎结算。
3. 群聊完整表现会增加公开场景风险，需要在提示词里控制措辞。
4. 强依赖记忆插件意味着依赖链更清晰，但部署时必须明确启用顺序。
5. 事件日志必须可追溯，方便后续解释“为什么升 / 为什么降”。
6. 结构化字段如果直接进入最终回复上下文，容易导致模型复读字段；注入层必须做自然语言化处理。

## 15. 测试建议与验收标准

建议补充以下回归测试：

1. 好感度边界值测试
2. 负向事件掉档测试
3. 恋人确认后锁档测试
4. 主动推进冷却测试
5. 每日回顾重复执行幂等测试
6. 记忆调用加分测试
7. 迁移旧羁绊初始值测试
8. 私聊 / 群聊同一全局状态测试
9. LLM 回复不泄露内部字段测试
10. 记忆 Provider 必需接口缺失时启动失败测试
11. `effective_stage` 在恋人锁档后不随分数回退测试
12. `idempotency_key` 重复写入不重复加分测试
13. `pending` 确认关系过期、拒绝和确认三条状态流转测试
14. 群聊主动确认默认关闭测试
15. 每日回顾 `dry_run` 不写库测试
16. 每日回顾 `force_rebuild` 先撤销再重算测试
17. 迁移重复执行跳过测试
18. 迁移 force 前备份测试
19. Bot 主动发起确认只进入 `pending`、不直接锁档测试
20. 用户明确同意后才写入 `confirmed_stage = 恋人` 测试

验收标准：

- 好感度任意写入路径都必须生成可追溯事件。
- 所有会改变分数的事件都必须有幂等键。
- 普通聊天回复不得出现 `好感度:`、`关系:`、`stage`、`affinity_score` 等内部字段。
- 记忆插件不可用时，好感插件应明确禁用，而不是静默降级。
- 迁移后新系统可独立运行，不再依赖旧羁绊展示逻辑。

## 17. 结论

本设计将现有羁绊系统升级为一个更完整的“好感度与关系系统”：

- 数值更直观
- 关系推进更自然
- 正负互动更有剧情感
- 记忆和关系职责分离
- 迁移成本可控
- 后续可继续扩展称呼、互动特权、专属提示等功能
